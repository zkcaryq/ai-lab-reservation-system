# intent / decision 两个 AI 能力说明

这两个能力在数据库里一直有占位（配置页能看到），但以前**没有任何代码调用**，配了也不生效。
现在它们已经接上，**未配置时行为与以前完全一致**，配置后自动生效。

两者都支持**两条调用路径**，按配置的模型名自动选择：

| 模型 | 走哪个接口 |
|---|---|
| `tongyi-intent-detect-v3` | OpenAI 兼容 **Chat Completions**（tag 模式） |
| `decision-model-preview` | **TypeSafe System One** `POST /compatible-mode/v1/systemone` |
| 其它任意文本模型 | 项目统一的 Responses API（JSON 提示词） |

> 这两个专用模型**只在百炼有**，MiniMax 没有。用专用模型时必须把供应商选成「百炼」。

---

## 一、intent（意图识别）—— 效果稳定，建议启用

**位置**：每次文本聊天，在知识检索**之前**。
**涉及接口**：`POST /api/ai/chat`、`POST /api/ai/chat/stream`（不影响 `/chat/image`）。

按官方文档，system prompt 给 tag 列表，模型只回一个字母（1 个 token，最快）：

| tag | 含义 | need_knowledge | 开启的工具 |
|---|---|---|---|
| `A` | 知识库问答（使用方法/规范/制度/开放安排/预约规则） | 是 | 无 |
| `B` | 实时数据查询（当前有哪些实验室、某实验室有哪些设备） | 否 | `list_open_labs`、`list_lab_equipments` |
| `C` | 创建预约（用户明确要求预约） | 是 | 三个工具全开 |
| `D` | 寒暄/无关闲聊 | 否 | 无 |

`need_knowledge=false` 时**跳过整条 RAG 检索**（省一次 embedding + 一次 rerank，约 1～1.5 秒）。

**实测（4/4 正确）**：

| 用户问题 | tag | 结果 |
|---|---|---|
| 你好 | D | 不检索、不给工具 |
| 六轴机械臂使用前要检查什么 | A | 检索，不给工具 |
| 现在有哪些实验室开着 | B | 不检索，给查询工具 |
| 帮我约明天下午的实验室 | C | 检索 + 三个工具全开 |

每次约 130 token。

## 二、decision（决策）—— 能力已就绪，但只能拦一种情况

**位置**：AI 生成预约草稿**之前**，只挂在 AI 预约这一条路径上。

它回答一个确定性代码回答不了的问题：**这些参数是用户说的，还是模型自己编的？**
`validate_reservation_request()` 只能判断参数「合法」，判断不了「用户到底有没有提过 14:00」。

### 它擅长什么、不擅长什么（实测结论）

这个模型擅长「从一段文本里判断某信息有无」，**不擅长「这句话是否支撑那个参数」**：

| 问法 | 结果 |
|---|---|
| 逐字段问「用户是否明确说明了开始时刻」 | 「只说下午」被判成已明确（P=0.88）❌ |
| 问「这份草稿能否提交确认」 | 「只说下午」被判 ready（0.88）❌ |
| `choice` 三选一（明确/模糊/没提） | 连「没说日期」都判 explicit（0.72）❌ |
| **抽取式：原话里有没有开始/结束的具体时刻** | 判别干净 ✅ |

对「日期」和「实验室对象」它更不靠谱——原话明明写了「人工智能实验室」，概率只有 0.04～0.28。

### 最终规则：只在「两个时刻都毫无信号」时才拦

```text
P(原话里有开始时刻) < 0.35  且  P(原话里有结束时刻) < 0.35
    → 判定用户压根没提时刻，拦下，让聊天模型追问
否则 → 放行
```

**为什么不按单字段拦**：模型对中文数字时刻很不稳定——「两点到三点」的结束能给 0.79，
但「十点到十一点」的结束只有 0.04、「四点半到六点」两项只有 0.49/0.45。
按单字段判定会把正常预约误拦，用户会陷入「反复追问同一句」的死循环。

**实测 9/9 正确**：

| 用户原话 | 结果 |
|---|---|
| 帮我约明天**下午**的实验室 | **拦**（start 0.11 / end 0.06） |
| 帮我预约 | **拦** |
| 帮我订明天下午的实验室 | **拦** |
| 帮我约明天下午三点 | 放（只说了开始，按保守规则不拦） |
| 帮我约明天下午两点到三点 | 放 |
| 帮我约明天上午十点到十一点 | 放 |
| 帮我约明天九点到十点 | 放 |
| 帮我约明天下午四点半到六点 | 放 |
| 帮我约明天 14:00-16:00 | 放 |

被拦下时，工具返回 `ok: false` + `unsupported_fields`，**聊天模型会自然转成一句追问**
（「您想约下午几点到几点？」），不会生成确认卡片。

### 它能拦 / 拦不住

- ✅ **能拦**：用户完全没提时间（「帮我约明天的实验室」「帮我预约」）——这是最常见的猜测场景。
- ❌ **拦不住**：用户只说了开始没说结束（「三点」），助手补的结束时间；
  以及日期、实验室对象被编造。这些交给确定性校验与确认卡片。

**误拦代价可控**：被拦时只是多问一句，不会丢数据。

## 三、配置建议

在「AI 模型配置」页点「配置」，两行分别填：

| 字段 | intent | decision |
|---|---|---|
| 供应商 | **百炼** | **百炼** |
| 模型 | 点「查询」选 `tongyi-intent-detect-v3`（列表第一项） | 点「查询」选 `decision-model-preview`（列表第一项） |
| Base URL | 与 OCR/向量那几行相同的 `.../compatible-mode/v1` | 同左 |
| 密钥 | 复用同一个百炼 Key | 同左 |
| 超时 | 10～15 秒 | 15～20 秒（代码兜底 20 秒） |
| 思考层级 | 不生效（代码固定关闭） | 不生效 |

> 查询模型列表时已做服务端筛选（`capabilities=TG`），并把专用模型排到第一位。

## 四、降级行为（重要）

这两者是**增强**，不是必需项。任何异常都退回旧行为：

| 情况 | intent | decision |
|---|---|---|
| 未配置 | 检索照常 + 工具全开（= 旧行为） | 放行（= 旧行为） |
| 调用失败 / 超时 / 鉴权失败 | 同上，写 `warning` 日志 | 同上，写 `warning` 日志 |
| 输出无法解析 | 同上，写 `warning` 日志 | 同上，写 `warning` 日志 |
| 模型明确给出结论 | 按结论执行 | 按结论执行 |

---

## 五、怎么确认已经生效

1. **看日志**：`logs/<UTC日期>/app-*.log`，搜 `intent classification failed` 或 `decision output`。
2. **看用量**：`GET /api/ai/usage/summary` 会出现 `capability = intent` / `decision` 的行。
3. **看效果**：问「你好」应该明显变快（跳过检索）；说「帮我约明天下午的实验室」应该被追问时段。

---

## 六、已知边界

- **intent 误判有代价**：把需要检索的问题判成 `D`，模型就答不出细节。tag 描述写在
  `intent_services.INTENT_TAG_SPECS`，需要时改描述文字。
- **decision 只拦「完全没提时刻」**，不拦日期/实验室/只给一半的情况，原因见第二节实测数据。
- **两者都不是安全边界**：预约真正的安全网仍然是「确认卡片 + 服务端全量校验 + 二次确认幂等」。
